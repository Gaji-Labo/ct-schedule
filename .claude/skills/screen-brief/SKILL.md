# 画面の要件を聞き取る

依頼内容: $ARGUMENTS

画面を作る前に、**事実**を人から聞き取って書く。見せ方の**判断**（レイアウト・部品・最初に見せる情報）は、Skill `implement-ui` が `docs/design/` をもとに行うので、ここでは決めない。

書いたファイルは、その画面を作るときも直すときも読まれる。依頼文はファイルに残さない（`experiments/prompts/` は検証で条件をそろえるための置き場所で、ここには書かない）。

## 0. 最初に読む

1. 依頼から、対象のアプリと画面を特定する。特定できなければ、最初にそれを聞く
2. `docs/design/apps/<アプリ名>.md` を読む。なければ新しいアプリとして扱い、画面の事実の前にアプリの事実も聞く
3. `docs/design/apps/<アプリ名>/screens/` に同じ画面のファイルがあれば読む。「3. 進め方」の「2) 振り分けて見せる」では、そこに書いてあることも埋まった項目として扱う
4. アプリの md と要件ファイルの「未決のこと」を拾っておく。「3. 進め方」の最初に「まだ決まっていないこと」として示す
5. 次を読み、読んで分かることは聞かない
   - `docs/design/principles.md`（社内アプリ共通の文脈）
   - 関係する既存の画面の Story（`src/design-system/pages/`）
   - アプリの実装の資料（`docs/apps/<アプリ名>.md`。あれば）

## 1. 埋める項目

### アプリの事実（アプリの md がないときだけ）

- 何のアプリか（1〜2文）
- 誰が、どんな場面で使うか
- 主な画面（名前・パス・目的）
- Storybook での名前

### 画面の事実

「区分」は、「3. 進め方」の「3) 足りないものだけ聞く」で使う。

| 項目 | 中身 | 区分 |
| --- | --- | --- |
| 目的 | この画面で利用者が何を済ませるか | 必ず聞く |
| 使う人と場面 | 誰が、いつ、どんな状況で、どの端末で開くか | 必ず聞く |
| 表示と操作 | エリア（情報のまとまり）ごとに、表示する項目（あれば例の値、件数・長さの目安）、操作（できること）、挙動（操作 → 結果） | 必ず聞く |
| 開き方と移動先 | URL、どこから開くか、どこへ移れるか | 聞く。分からなければ未決 |
| 状態で変わること | ログインの有無、権限、データの状態（0件・お休みなど）で変わること | 聞く。分からなければ未決 |
| こうなると困ること | 利用者がつまずくと困る場面（例: 次に押すボタンが分からず、記録を忘れる）。どう見せて防ぐかではなく、場面で聞く | 聞く。分からなければ未決 |
| 決まっている文言 | ボタン名、空状態の文言など、すでに決まっているもの | 聞かない。書き出しにあれば書く |
| 決まっていること（見せ方） | プロダクトとして決まっている見せ方 | 聞かない。書き出しにあれば書く |

## 2. 聞かないこと

- レイアウト・並べ方、部品の選び方、色・余白・文字
- 最初に目に入るべき情報や、情報の優先順位

これらは `implement-ui` が判断し、その判断を人が確かめる。人が書き出しや答えの中で言ったときだけ、要件ファイルの「決まっていること（見せ方）」に書く。こちらから答えを提案しない。

## 3. 進め方

### 1) 書き出してもらう

「0. 最初に読む」で拾った未決があれば、最初に「ここはまだ決まっていません」と一覧で示し、今決められるものがあるかを聞く。

そのうえで、決まっていることを順番や形式を気にせず書き出してもらう。箇条書きや断片でよく、既存の資料（機能要件を並べた依頼文、仕様のメモなど）を貼ってもらってもよい。項目を順に聞いていくことはしない。

依頼にすでに要件が書いてあれば、それを書き出しとして扱い、追加があるかだけを聞く。

要件ファイルがすでにあり、`implement-ui` のまとめ（足りないこと・食い違うところ）を受けて来たときは、書き出しを求めない。まとめに挙がった項目だけを「3) 足りないものだけ聞く」で聞く。

### 2) 振り分けて見せる

書き出しと、「0. 最初に読む」で読んだファイルから分かることを、「1. 埋める項目」の項目ごとに振り分けて見せる。どの項目が埋まり、どれが空いているかも示す。

- 書き出された言葉はそのまま使う。要約したり、言い換えて意味を変えたりしない
- 見せ方の答え（「テーブルで」「インラインで」など）は「決まっていること（見せ方）」に入れる
- 画面をまたぐ要件（ヘッダー・フッターなど）は、要件ファイルではなくアプリの md の候補として分けて示す
- どの項目に入るか分からないものは、推測で振り分けずに聞く
- 振り分け違いがあれば直してもらう

### 3) 足りないものだけ聞く

空いている項目を、「1. 埋める項目」の区分に沿って聞く。

- 「必ず聞く」項目が埋まるまで聞く
- 「分からなければ未決」の項目は1回だけ聞き、答えがなければ「未決」にする
- 「聞かない」項目は聞かない
- 1回に聞くのは3問まで。答えやすいよう、例か選択肢を添える
- 「分からない」「あとで決める」と言われた項目は「未決」にして先へ進む。推測で埋めない

## 4. 書く

### 画面の要件ファイル

`docs/design/apps/<アプリ名>/screens/<画面>.md` に書く。ファイル名は英小文字とハイフン（例: `my-page.md`）。

```markdown
# <画面名（日本語）>

- アプリ: [<アプリ名>](../../<アプリ名>.md)

## 目的

## 使う人と場面

## 開き方と移動先

- URL: 
- どこから開くか: 
- どこへ移れるか: 

## 表示と操作

### <エリア名>

| 表示 | 内容 |
| --- | --- |
| 項目 | あれば例の値、件数・長さの目安 |

| 操作 | 挙動 |
| --- | --- |
| できること | 操作 → 結果 |

## 状態で変わること

## こうなると困ること

## 決まっている文言

## 決まっていること（見せ方）

人から言われたときだけ書く。なければ見出しごと消す。

## 未決のこと

- 未決: <何が決まっていないか>（決める人: <分かれば>）
```

- エリアは情報のまとまりとして分ける。画面のどこに置くかは書かない
- エリアの中は表で書く。人が手で書いた依頼文（箇条書き）を写すときも、この表に直す
- ログインの有無、権限、データの状態で変わることは「状態で変わること」にまとめ、操作ごとに条件を散らさない
- 答えがなかった項目は、見出しを残して中身を「未決のこと」に回す
- 未決は中身で置き場所を分ける。その画面だけのことは要件ファイルの「未決のこと」、アプリ全体にかかわること（並び順の決まり、空状態の文言の方針など）はアプリの md の「未決のこと」に書く
- 「0. 最初に読む」で拾った未決が決まったら、決まった内容を該当する見出しに書き、「未決」の行を消す
- 人の言葉を言い換えて意味を変えない。文言は聞いたとおりに書く

### アプリの md

- **ないとき**: `docs/design/apps/<アプリ名>.md` を下のひな形で作る。中身を書くのは「Storybook での名前」「何のアプリか」「主な画面」「ユーザーと利用シーン」と、アプリ全体の未決だけ。ほかの見出しは置くだけにする（生成を重ねて足していく）
- **あるとき**: 「主な画面」の表に行を足し、目的の欄から要件ファイルにリンクする。アプリ全体の未決が出たら「未決のこと」に足す（節がなければ最後に作る）。ほかの節は変えない

```markdown
# アプリの文脈: <アプリ名>

<アプリ名> 固有の目的・画面・利用シーン・原則。社内アプリ共通の文脈と原則は [../principles.md](../principles.md) にある。

- Storybook での名前: `<アプリ名>`（部品は `Apps/<アプリ名>/Components/`、画面は `Apps/<アプリ名>/Pages/`、確認待ちの画面は `Drafts/<アプリ名>/`）

## 何のアプリか

## 用語

## 主な画面

| 画面 | パス | 目的 |
| --- | --- | --- |
| <画面名> | `<パス>` | <目的>（[要件](./<アプリ名>/screens/<画面>.md)） |

## ユーザーと利用シーン

## このアプリ固有の原則

## このアプリ固有の色

## このアプリ固有の部品

## Story で用意する状態

## 未決のこと

- 未決: <何が決まっていないか>（決める人: <分かれば>）
```

- アプリの実装の資料（`docs/apps/<アプリ名>.md`）があれば、冒頭の段落にリンクを足す

Story・コード・依頼文のファイルは作らない。

## 5. 確かめて渡す

1. 書いた・変えたファイルと、「未決のこと」の件数（要件ファイルとアプリの md のそれぞれ）を示す
2. 人に内容を確かめてもらう。直す点があれば直す
3. 確かめてもらえたら、次は `/implement-ui <画面名>` で作ると案内する。このスキルからは作り始めない

未決のまま作り始めるか、先に決めるかは人が選ぶ。未決のまま作るときは、`implement-ui` がその項目を推測で決め、推測として記録する。
