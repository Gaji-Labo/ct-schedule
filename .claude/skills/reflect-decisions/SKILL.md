# 決めたことを戻し先に書き足す

依頼内容: $ARGUMENTS

Skill `implement-ui` で作った画面を人が確認し、決めたことを、次の生成で読まれる場所に書き足す。**書く前に、書く内容を人に見せて承認を取る。承認されていないものは書かない。**

## 0. 最初に読む

1. `.implement-ui/report.json` を読む（`guesses` の `topic`・`decision`・`scope`・`fix`）。やり直したあとは前回の推測が上書きされているので、足りなければ人に聞く
2. 対象の画面の要件ファイル（`docs/design/apps/<アプリ名>/screens/<画面>.md`）と、アプリの md（`docs/design/apps/<アプリ名>.md`）を読む。どちらも「未決のこと」を拾う
3. `docs/design/workflow.md`「フィードバックの戻し先」を読む

## 1. 決めたことを集める

Skill `implement-ui` から呼ばれたときは、そこで控えておいた決めたことから始め、まだ答えのない推測と未決だけを聞く。この Skill から始めたときは、推測と未決を一覧にして見せ、それぞれをどうするかを人に聞く。

| 扱い | 意味 |
| --- | --- |
| そのまま採る | AI の推測（`decision`）のとおりに決める |
| 直して採る | 人が答えを直して決める |
| 保留 | まだ決めない。未決として残す |

- 推測と未決のほかに、人が確認で出した指摘（「ここはこうしてほしい」）があれば、それも集める
- 人が決めていないことを、AI が決めたことにしない

## 2. 書き先を決める

| 決めたこと | 書き先 |
| --- | --- |
| その画面だけのこと（`scope: "app"`） | 画面の要件ファイルの該当する見出し |
| アプリ全体にかかわること（`scope: "app"`） | アプリの md の該当する節 |
| どのアプリでも同じ答えになること（`scope: "system"`） | `workflow.md`「フィードバックの戻し先」の表に沿う（`rules.md`、`principles.md`、ガイドライン、Story の docs、Skill） |
| 未決への答え | 該当する見出しに書き、「未決のこと」の行を消す |
| 保留 | 未決として、要件ファイルかアプリの md の「未決のこと」に足す（すでにあれば何もしない） |

迷ったら「別の社内アプリで同じ種類の画面を作っても、同じ答えになるか」で `app` と `system` を分ける。`app` のうち、画面の要件ファイルとアプリの md は「同じアプリのほかの画面にもかかわるか」で分ける（例: その画面の空状態の文言は要件ファイル、メンバーの並び順の決まりはアプリの md）。`report.json` の `fix.where` は参考にするが、上の表とずれていたら表を優先する。

## 3. 書く内容を見せて承認を取る

ファイルごとに、次をまとめて見せる。

- 書くファイルと見出し
- 足す・変える文（変える場合は、変える前と後）
- 消す「未決」の行

人の答えは「承認」「直して承認」「書かない」のどれか。承認されたものだけを「4. 書く」で書く。一部だけの承認もできる。

## 4. 書く

- 承認された文だけを、見せたとおりに書く。承認のあとで言い回しを変えない
- 見出しの構成は変えない。足す場所がない内容は、書く前に見出しの案を見せて承認を取る
- 部品やトークンの変更（コードの変更）が必要なものは書かない。「別の作業として直す必要があるもの」として報告に回す

## 5. 報告する

- 書いたファイルと見出し
- 消した未決、残した未決（保留）の件数
- 書かなかったもの（承認されなかったもの、コードの変更が必要なもの）

この Skill はコミットしない。コミットするかは人が決める。
