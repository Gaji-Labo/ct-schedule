# Harness² 改善ループ 中間レポート（2026-10-28）

「要件ファイルから、デザイナーの意図どおりの画面を Storybook に作る」ハーネス（`CLAUDE.md` と Skill `implement-ui` / `screen-brief` / `reflect-decisions`）を、[Harness²](https://github.com/google-research/harness2) の改善ループで直せるかを試している。起点は `feature/screen-brief-skill`（a768ad99dd）、参考は PR #112・#129。

**現時点のまとめ**

- 仕組みは一通り動いた。要件 → codex が Story を作る → Claude が軌跡を読んでハーネスを直す → 採点、まで回る
- 4タスクのうち、結果がそろったのは **マイページだけ**。skip-weeks は一部、schedule-v2・member は未実施。codex のワークスペースの利用上限（spend cap）に3回当たった
- 改善側は2回とも独立に「Story を書いたあと、要件と突き合わせて削る工程」を Skill として足した。マイページでは点が上がる傾向があるが、採点のぶれ（±1）と回数（各1回）から、まだ効果があるとは言えない
- どのハーネスでも直らなかった失敗がある: 要件に無い説明文・重複を足す、主要な操作を PageHeader の右端に置かない

### 仕組みを作った（`experiments/harness2/`、未コミット）

| `member` | 既存画面の再現 | 後退していないか | 8 |

ループは K=1 parallel。1タスクにつき4つのハーネスを試す。

| ラベル | ハーネス |
| --- | --- |
| base1 | 今の CLAUDE.md と Skill そのまま |
| inv1 | 改善側の「汎用の」編集（進め方・道具） |
| dom1 | 改善側の「この領域の」編集（画面づくりの知識） |
| agg1 | inv1 と dom1 の合成 |

タスクは順に回り、前のタスクの教訓（`EXPERIENCE.md`）が次のタスクの改善に引き継がれる。

途中で直したこと:

- rollout 中のネットワークを許可（Storybook ビルドが Google Fonts を取りに行く）

- 実行側の既定モデルを gpt-6.1-sol に（Astra は数 rollout で上限に達した）

## 4. 修正の候補（見送ったもの）

どれも、実際の `CLAUDE.md`・Skill・`docs/design/`・`package.json` には反映していない。結果がそろう前に戻すと、何が効いたか分からなくなるため。

| 候補 | 戻し先 | 根拠 | 見送った理由 |
| --- | --- | --- | --- |
| Story を書いたあとの見直し（要件との対応表・文言の完全一致・重複を削る・メッセージの出し先） | Skill `implement-ui` の手順 | r1・r2 で改善側が独立に提案。reproduce-02 の人の結論と同じ。マイページで点が上がる傾向 | 差が採点のぶれの範囲。合成 agg1 では効いていない。skip-weeks・schedule-v2 で確かめていない |
| 画面の主要な操作は `PageHeader` の右端に置く、を確認項目にする | `implement-ui` の確認項目、または PageHeader のガイドライン | skip-weeks で、完了・打ち切りを問わず全ハーネスが PageSection の中に置いた | 1タスクだけの観察。rules.md には既に書いてあるので、書く場所より読ませ方の問題かもしれない |
| `verify:ui` に `tsc --noEmit` を足す | `package.json` | マイページの rollout で Story の型エラーが Storybook ビルドを素通りした（r2 inv1 の改善側が指摘）。`verify:ui` は lint・test・ビルドだけ | ハーネスの外（リポジトリの設定）の変更。既存ファイルの型エラーの有無を確かめていない |
| 要件に無い要素（説明文・補足・カウンタ）を足したら、理由を報告に書かせる | `implement-ui` | マイページ項目9、skip-weeks 項目11 で、ほぼ全ハーネスが落ちた | 見直しの Skill（1つ目）でも防げなかった。書かせるだけで減るかは未確認 |
| はみ出しを測るスクリプト（`check_overflow.py`） | `implement-ui` の確認手順 | r1・r2 の inv1 が提案 | rollout の中で確かめきれず `unchecked` で終わった。手元（Claude Code）ではブラウザで確かめられるので、そのままは要らない |
| 日本語を含む stdin の Python が失敗したときのヒント（フック） | — | r2 skip-weeks の inv1 が提案 | codex の実行環境だけの問題 |
| `report:ui` の実体の場所の注記 | — | r1・r2 の inv1 | この実験の環境（Skill を `.agents/` に写したこと）だけの問題 |

## 5. 次にやること

1. spend cap が戻ったら r2 を再開する（同じコマンドで、上限で失敗した rollout からやり直す）。残り: skip-weeks の inv1 / dom1 / agg1、schedule-v2、member
2. 採点のぶれを減らす。ハーネスごとに rollout を2回以上（`--k 2`、または同じタグを別 seed で）にするか、採点を2回して多数決にする
3. 採点基準（`tasks/*/rubric.md`）をデザイナーに見てもらう。今は叩き台のまま
4. 結果がそろったら、見送った候補のうち複数タスクで効いたものを、根拠をつけて PR で戻す。戻したら起点を新しいコミットにして、基底の点が上がるかを見る
