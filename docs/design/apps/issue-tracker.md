Issueトラッカー固有の目的・画面・利用シーン・原則。社内アプリ共通の文脈と原則は [../principles.md](../principles.md) にある。

- Storybook での名前: `Issueトラッカー`（部品は `Apps/Issueトラッカー/Components/`、画面は `Apps/Issueトラッカー/Pages/`、確認待ちの画面は `Drafts/Issueトラッカー/`）

## 何のアプリか

チームの開発リポジトリに寄せられた不具合の報告や要望（Issue）を記録し、探し、誰が取り組むかを決めるためのアプリ。リポジトリには外部の人も Issue を書き込める。

## 用語

| 用語 | 意味 |
| --- | --- |
| **Issue** | 1件の不具合の報告・要望・質問。番号（例: #14931）で呼ぶ |
| **オープン / クローズ** | Issue の状態。クローズには「完了」と「対応しない」の2種類がある |
| **ラベル** | Issue に付ける分類（例: `bug`、`enhancement`、`needs-triage`）。ラベルごとに色が決まっている |
| **担当者** | その Issue に取り組む人。いないこともある |
| **マイルストーン** | リリースなどの区切り。Issue をまとめる単位 |
| **プルリクエスト** | Issue を解決するコードの変更。Issue に紐づけられる |

## 主な画面

| 画面 | パス | 目的 |
| --- | --- | --- |
| Issue一覧 | `/issues` | リポジトリの Issue を探し、状態を確かめ、新しく起票する入口（[要件](./issue-tracker/screens/issue-list.md)） |
| Issue詳細 | 未決 | 今回は対象外 |

## ユーザーと利用シーン

- 保守するチームのメンバーが、1日に何度も開く。自分の担当の確認、新しく来た Issue の振り分け、似た Issue が無いかの確認
- 外から来た人が、起票の前に同じ報告が無いかを探す
- 件数が多い（オープン 1,048件、クローズ 5,614件）。1ページに25件ずつ出す
